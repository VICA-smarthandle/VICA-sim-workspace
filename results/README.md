# 폭 측정 결과

각 JSON 하나가 한 패스다. 시뮬레이터를 새로 띄우고, nav2 를 올리고, 목표를 하나
보내고, 결과를 적는다. 한 패스에 약 5분.

`track` 배열이 파일 크기의 대부분을 차지한다. `[시각, x, y, yaw]` 가 1,400점쯤
들어 있고, `animate_run` 이 이걸로 영상을 만든다. 지우면 영상을 다시 못 만든다.

## 읽는 법

```bash
ros2 run vica_description width_report results/20kg/dwb_infl0.55
```

`width_report` 는 **`course_stamp` 가 다른 결과를 한 표에 넣지 않는다.** 이건
편의가 아니라 이 디렉터리가 존재하는 이유에 가깝다 — 2026-08-07 에 서로 다른
코스에서 나온 두 스윕을 비교해서, 같은 "1.20 m" 가 한쪽에서는 x=6.10, 다른 쪽에서는
x=11.20 의 목표를 뜻하는 표를 몇 시간 동안 컨트롤러 결과로 읽었다. 두 표 모두
완성돼 보였고 어느 쪽도 자기가 어떤 코스를 돌았는지 적어두지 않았다.

## 무엇이 들어 있나

| 디렉터리 | 로봇 질량 | 코스 스탬프 | 내용 |
| --- | --- | --- | --- |
| `20kg/` | 20.0 kg (실측) | 2026-08-07 14:37:54 | DWB 1.40/1.20/1.15, MPPI 1.40/1.20/1.15 |
| `94kg/` | 94.28 kg (URDF 오류) | 2026-08-07 08:56:39 | DWB 9폭 27패스, MPPI 9폭 27패스 |

`94kg/` 는 폐기가 아니다. URDF 가 실물의 4.71 배 무거운 로봇을 기술하고 있던
동안의 측정이고, 질량을 고친 뒤 결과가 어떻게 달라졌는지가 이 프로젝트에서
확인된 사실 중 하나다. 1.15 m 레인이 `0/3` 에서 `2/3` 이 됐다.

`course_stamp` 가 다르므로 두 디렉터리는 자동으로 섞이지 않는다.

## 이 숫자들이 나오기까지 고친 것

이 결과들 이전의 측정은 신뢰할 수 없다. 하네스에 다음이 있었다.

- `--spawn` 에 음수 값을 넘기면 argparse 가 옵션으로 읽어 실패했다. 코스 왼쪽
  절반, 즉 좁은 레인 네 개는 한 번도 측정된 적이 없었다.
- AMCL 이 시드를 반영하기 전의 포즈를 출발로 기록하고, 목표도 그때 보냈다.
  로봇은 스폰에서 1 mm 도 움직이지 않았는데 출발 위치가 3.2 m 어긋난 것으로
  적혔다.
- 스윕이 `width_trials` 출력을 grep 으로 걸러서, 거부 메시지가 전부 삭제됐다.
  27 패스 중 12 패스가 아무 흔적 없이 사라졌다.
- 라이다 자기 반사 제외 섹터가 실측(±2.3°)의 여덟 배인 ±20° 여서, 뒤쪽 40° 호의
  진짜 반사를 버리고 있었다.
- `from` 을 `odom.clear()` 앞에서, `to` 를 뒤에서 읽어 `moved` 가 원점이 다른 두
  포즈의 차이였다.

## 재생성

```bash
RESULTS_DIR=/tmp/vica_width_x bash src/vica_description/scripts/width_sweep.sh dwb 1.40 1.20 1.15
```

이미 있는 결과 파일은 건너뛴다. 중간에 멈춰도 같은 명령으로 이어서 돌면 된다.
